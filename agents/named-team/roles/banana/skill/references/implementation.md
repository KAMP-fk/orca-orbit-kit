# 実装・検証・PR / CI

[contracts.md](contracts.md) の対象・受入条件・権限・完了条件に沿って進める。

## Checkout と変更

作業開始時に branch / full SHA と `git status --short` を確認する。
未コミット・未追跡・未 push の作業は保全し、他担当の作業を reset / clean で消さない。
基準 branch と必要な fetch は repo の手順に従う。Orca 管理の checkout は `orca-cli` で管理する。
既存の担当 branch / PR を再利用し、branch 名・Issue と PR の関係はその repo の規約を使う。

既存コードの命名・型・責務に合わせ、同じ処理を `rg` で探して再利用する。
依頼された範囲の変更に絞り、無関係な整形や新しい依存を混ぜない。
特定 id / テナントのデータ修正をスキーマ migration に押し込まず、プロジェクトの運用経路を使う。

## 検証と提出

編集中は影響範囲の検査を使い、push 前はプロジェクトが要求する必須検査を通す。
`concafe-techo` の push 前 `pnpm check` を省かない。
新しい挙動・失敗経路・境界値を守るテストを使い、実装の形だけを写すテストを増やさない。
テストの件数と、何を検証したかを分けて示す。
落ちた検査を skip / any / 握りつぶしで通過扱いにしない。

委任範囲内で commit / push / PR を行う。PR は目的・結果・検証を読める状態にする。
PR 作成だけを依頼の完了条件と取り違えない。
現在 head の CI、[review.md](review.md) の独立レビュー、指摘修正、該当する merge 後の条件まで追う。
手動 Ready / merge の禁止など対象契約のゲートを維持する。

## PR に載せる根拠

具体的な問題と変更後の挙動を先に書き、なぜ必要かと確認結果を続ける。
仕様や受入条件に対して、確認済みと未確認の範囲を示す。会話ログは貼らない。

| 変更 | 有効な根拠 |
|---|---|
| 整形・移動 | 意味を保つ diff / AST 等と必要な検査。空白除去の hash だけでは挙動不変と断定しない |
| 依存更新 | lockfile の変更範囲、互換性に関わる検査 |
| 設定変更 | 実際の前後の挙動、対象 SHA と観測ログ / CI run |
| 挙動変更 | AC と対応する実装・テスト・観測結果、まだ確かめていない経路 |

呼び出し元・画面・API・job・テーブル等の影響は現物を読んで示す。
手動 QA が残る場合は前提 / 操作 / 期待 / 確認場所を、未確認の重要な範囲から書く。
小さな変更は短く、実施者・日時は実際に通した人が記録する。空欄を検証済みと読まない。

提出前に差分を読み、一時ファイル、不要な依存、目的外の変更、漏れた検証がないか確認する。
チェックの定型文を貼るだけで済ませず、実際に行った検査と結果を記す。
