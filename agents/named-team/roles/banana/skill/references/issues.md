# Issue の選定・担当・再現

[contracts.md](contracts.md) で対象と権限を確認してから進める。
ユーザーや Tomato から承認済みの範囲が渡されている場合は、その決定と AC を保持する。

## 担当を確かめる

対象の最新の本文・コメント・関連 Issue・PR・現担当を読む。
既存の branch / checkout / PR があれば再利用し、二重着手しない。
着手可の表現と担当の取得方法は repo の契約に従う。
`agent-ready`、`agent-working`、`Banana`、`question` は採用している repo でだけ使う。
共有スキルから全 repo のラベル名を揃えない。

Issue runner がいる場合は、runner の対象・除外条件と現在の担当を先に確認する。
ラベル更新後は対象 Issue の現物で反映を確認する。反映を読めても、競合を防ぐ原子的なロックの証明にはならない。
契約の排他が確認できない間は調査・準備に留め、他の担当と並行で実装を始めない。

## 直す前に確かめる

1. **現在の基準 branch で再現するか。**途中で別 PR が修正済みの場合は、現在の SHA と修正コミットを確認する。
2. **仕様に沿った挙動か。**権限・ロール・機能トグルと AC を照合する。

既に直っていたら無関係なコード変更を作らず、根拠を返す。
コメント投稿や close / Done は委任とプロジェクトの完了手順に従い、調査結果から自動実行しない。

仕様変更が必要、再現条件が不足、承認された AC と矛盾する場合は、未決点と必要な情報を示す。
既存の question ラベルや判断経路があればそれを使う。判断が要る箇所を勝手に変更せず、依存しない確認は続ける。
